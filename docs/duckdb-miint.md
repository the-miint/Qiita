`duckdb-miint` is the DuckDB extension that powers all bioinformatics SQL in qiita — the data plane links it in, native orchestrator jobs invoke its functions, and several reference-data ingestion steps are thin wrappers around its table functions. Treat this file as the index: when you need a real signature, click through to the upstream doc rather than trusting paraphrased examples here.

**Rendered upstream docs: <https://the-miint.github.io/duckdb-miint/>** — browsable, and the fastest way to see a function or writer's FULL parameter list (e.g. the COPY writers live at `/writing/`).

> ### A probe cannot establish absence — read the reference for capability questions
>
> The rule in `CLAUDE.local.md` ("install it and assert, don't reason about it") is about **behaviour**: what does this function do with this input. It does **not** answer **capability** questions — "can miint do Y?" — and using an experiment for those is actively misleading, because a failed attempt only shows *the thing you tried* didn't work, not that the feature is absent.
>
> This is not hypothetical. `FORMAT BAM`'s SEQ support was missed exactly this way: a probe joined a sequence *column* into the copied relation, saw `SEQ` stay `*`, and concluded "this writer cannot emit SEQ" — which was written into a job docstring, this file, and the changelog. The real interface is a **`SEQUENCE_DATA` table parameter**, documented upstream all along. The probe tested a guess at the API and confirmed the guess was wrong, nothing more.
>
> So: for "does X support Y?", the authorities are the **catalog** and the **docs** — never an experiment.
>
> **Step 1 — ask the catalog. It is the loaded binary describing itself, so it cannot be stale.** One query answers "does this exist" and "what can I pass it":
>
> ```sql
> SELECT function_name, function_type, parameters, parameter_types, macro_definition
> FROM duckdb_functions() WHERE function_name = 'align_minimap2';
> ```
>
> What you get back, by function kind:
>
> | Kind | Exists? | Parameters | Body |
> | --- | --- | --- | --- |
> | table function (`align_minimap2`, `rype_classify`, …) | yes | **all named params listed** — `align_minimap2` shows all 10 (`preset`, `max_secondary`, `eqx`, `k`, `w`, …) | — |
> | macro / table_macro (`read_gff`, `genome_coverage`, `infer_trim`, …) | yes | **real argument names** (`alignments`, `subject_total_length`, …) | **`macro_definition` is the full SQL body — read it** |
> | scalar / aggregate (`filter_read`, `cigar_*`, …) | yes | every **overload arity** (names are `col0…colN`) | — |
> | **COPY writer (`FORMAT BAM`, `UBAM`, …)** | **NO — invisible** | **none** | — |
>
> For a macro this is better than the docs: `SELECT macro_definition FROM duckdb_functions() WHERE function_name='read_gff'` shows it is a `read_csv` with no `##FASTA` handling. That *is* the `##FASTA` bug, visible in one query.
>
> **Step 2 — read the docs, always, for the two things the catalog cannot tell you:**
> - **COPY writers — the one real blind spot.** DuckDB has no `duckdb_copy_functions()` system table, so `FORMAT BAM` and its options do not appear in the catalog **at all**. Worse, `CopyFunction` has no named-parameter declaration anywhere in DuckDB: miint's option names exist only as branch conditions inside each writer's bind. Nothing can enumerate them, which is exactly how the `SEQUENCE_DATA` miss happened. Tracked upstream as **[duckdb-miint#196](https://github.com/the-miint/duckdb-miint/issues/196)** (a `miint_copy_options()` introspection function + errors that list the valid set). **Until that lands, see [Interim recipe](#interim-getting-a-copy-writers-real-option-list) below.**
> - **Semantics.** The catalog shows that `read_gff` takes a `path` and that `read_alignments` returns a `stop_position`. It does **not** show that one is inclusive and the other exclusive, that `alignment_slice` NULLs tags on trimmed reads, or that `read_ena_sequences` can skip runs. Every trap in this file is of that kind. **Signatures come from the catalog; meaning comes from the docs.**
>
> **Before writing "miint cannot …" anywhere** — comment, changelog, issue, or chat — do both steps. Absence claims get copied forward unchallenged, because nobody re-probes a documented dead end. And a `BinderException` naming one parameter is proof there is a parameter *list*: `COPY FORMAT BAM requires REFERENCE_LENGTHS parameter` should send you to `docs/writing.md`, not just make you add that one argument.

## Install / version probe

```sql
INSTALL miint FROM community;
LOAD miint;
SELECT miint_version();          -- extension build SHA — the first sanity check
SELECT * FROM miint_versions();  -- every embedded tool version (see below)
```

**`miint_warnings()` is not a load-time probe** — an earlier revision of this file described it as one ("non-fatal load-time issues, e.g. GPL boundary not installed"), which is wrong twice over: a missing gpl-boundary is reported by *throwing* at call time, not by a warning row, and the table is empty on a clean load.

It is a **runtime, per-query log of non-fatal warnings**, and it matters because some functions **degrade silently rather than failing**. The one that should worry qiita is `read_ena_sequences`, which skips or retries individual runs and still returns a successful-looking result — the skipped runs appear only here:

```sql
SELECT * FROM read_ena_sequences(...);
SELECT * FROM miint_warnings();  -- e.g. "run 'ERR1234567' failed on retry (...), skipping"
```

**Check it after any ENA ingest.** A partial result that reports success is otherwise indistinguishable from a complete one.

Local builds need `allow_unsigned_extensions=true` and `LOAD '/path/to/miint.duckdb_extension'`. There is also a companion Python CLI named `miint` (lives under `python/` in the repo) that wraps the extension for `convert`/`transform`/`align` subcommands — not on PyPI; install from a local checkout with `pip install -e python/`.

**In qiita, don't `INSTALL ... FROM community`.** Every component runs the same team-mirror build, single-sourced in [`qiita_common.duckdb_miint`](../qiita-common/src/qiita_common/duckdb_miint.py) (`MIINT_EXTENSION_REPO` overrides for a local/dev build; the mirror build is unsigned, so `allow_unsigned_extensions=true` is always set). On the cluster the extension is **pre-staged once at deploy** into `MIINT_EXTENSION_DIRECTORY` (`scripts/stage-miint-extension.sh`); the CO service, the native SLURM jobs, the compute-readiness probe, and the control plane's masked-read streamer (`connect_with_miint_staged`) then only `LOAD miint` — no per-job download, no compute-node mirror dependency, no writable-`$HOME` requirement. The client-side `qiita reference load` CLI, which can't reach a deploy-staged dir, does a plain cached `INSTALL` instead. The Rust data plane honors the same `MIINT_EXTENSION_REPO` / `MIINT_EXTENSION_DIRECTORY` env contract independently (it can't import the Python module — keep the two in sync). DuckDB namespaces the staged dir by version + platform, so re-run the stage step on a miint or DuckDB bump.

## Function inventory

Signatures are abbreviated — go to the upstream `.md` for full parameter docs. `[param=default]` denotes a named optional parameter.

### Scalar (per-row) — `docs/alignment_analysis.md`, `docs/utilities.md`
- SAM flag predicates: the **`alignment_is_*` family** — `alignment_is_paired` / `_proper_pair` / `_unmapped` / `_mate_unmapped` / `_reverse` / `_mate_reverse` / `_read1` / `_read2` / `_secondary` / `_primary` / `_qc_failed` / `_duplicate` / `_supplementary`, plus HTSlib-compatible aliases (`is_unmapped`, `is_secondary`, `is_dup`, `is_qcfail`, …). Each takes the `USMALLINT` `flags` column and returns BOOLEAN. **Use these — do not hand-roll bit math on `flags`.** Use **`alignment_is_mapped_primary(flags)`** when you mean "a real, mapped primary alignment": `alignment_is_primary` follows the SAM spec's *primary line* definition (`FLAG & 0x900 == 0`) and is therefore **TRUE for an unmapped read**. Upstream documents this explicitly, including the unmapped caveat — see `docs/alignment_analysis.md`. Pinned qiita-side in `qiita-compute-orchestrator/tests/jobs/test_syndna_smoke.py::test_mapped_primary_predicate`.
- `alignment_seq_identity(cigar, nm, md, type)` — identity from CIGAR + NM/MD tags
- `cigar_sequence_identity(cigar)` — identity from the CIGAR **alone, no tags**. **qiita-verified 2026-07-13** (mirror `5447847`): on minimap2's eqx CIGAR (`=`/`X`) it reproduces `alignment_seq_identity(..., 'blast')` EXACTLY (probed 0.98 / 0.993 / 0.9709 on reads carrying mismatches and a 30 bp deletion). This matters because **`alignment_slice` NULLs `tag_nm`/`tag_md` on any read it TRIMS**, which makes `alignment_seq_identity` return NULL on precisely the boundary-spanning reads — so `cigar_sequence_identity` is the function to score a SLICED alignment with. Pair it with `cigar_query_coverage` for the alignment ratio; between them the tags are redundant. Used by `align_sharded`'s identity gate.
- `cigar_query_length(cigar, [include_hard_clips=true])`
- `cigar_query_coverage(cigar, [type='aligned'])` — **per-RECORD, and it cannot see a read's other records.** A read the aligner split across records — a supplementary alignment, or a read crossing the **origin of a circular reference** held as a linear contig — has each record covering only its own share of the query, so no record clears a floor like 0.90 even when the fragments together explain the read fully. Upstream documents this and ships the pooling for it: **`circular_query_coverage(alignments, reference_lengths, [coverage_type='aligned'])`** (table macro; both args are RELATIONS, not name strings), **`cigar_pooled_identity(cigar)`** (aggregate) and **`cigar_query_intervals(cigar, flags, [type])`** (scalar). Contract, caveats and the wrap-vs-chimera evidence columns are at <https://the-miint.github.io/duckdb-miint/alignment_analysis/#circular-query-coverage> — read it there rather than from a paraphrase. All three are present in mirror build `9fc4d12`. `reference_lengths` needs `(reference, length, is_circular)`; `is_circular` is required per reference and a NULL is rejected rather than assumed, because nothing in an alignment records circularity.
  - **qiita consequence, and it is a live one:** `align_sharded` applies `_MIN_QUERY_COVERAGE_MINIMAP2` (0.90) **per SAM record** in its phase-1 COPY, so a long read crossing a circular contig's origin is dropped before it reaches `alignment` at all — the loss is silent and concentrated at the origin of exactly the references most often recovered as complete circles (closed chromosomes, plasmids, phages). The repo's only pooled gate is the concatenating `string_agg(cigar, '')` idiom above, which recovers **identity but not coverage**: a clip consumes query length without being an aligned column, so each fragment's clip of the other re-enters the denominator. **qiita-verified 2026-08-20** (mirror `9fc4d12`, minimap2 `0477498`), 20 kb contig / 6 kb origin-spanning read against a same-length mid-contig control: 2 records at `cigar_query_coverage` 0.5 and `cigar_sequence_identity` 1.0 each; concatenated, 0.5 coverage but 1.0 identity; `circular_query_coverage`, 1.0 coverage over 2 fragments. Pinned by `qiita-compute-orchestrator/tests/jobs/test_align_sharded.py::test_origin_spanning_read_splits_into_one_record_per_side`, which asserts each score against the constant. The DuckLake `alignment_origin_spanning` table declares its `pooled_coverage` / `pooled_identity` columns as `circular_query_coverage`'s `coverage` / `identity`.
- **Both CIGAR scorers are PERMUTATION-INVARIANT over a concatenated CIGAR** — `cigar_sequence_identity` and `cigar_query_coverage` return the same value however the ops are ordered. **qiita-verified 2026-07-29**: all 120 permutations of `150=` / `75=75X` / `100=2I48=` / `20=130S` / `60=1D89=` (an indel and a soft clip included, so the op mix would break a naive left-to-right accumulator) score one distinct `(identity, coverage)` = `(0.8742, 0.8238)`. **Upstream documents this** — `docs/alignment_analysis.md` states `cigar_sequence_identity` is additive over CIGAR ops (`#= / (M+I+D)`) and documents the fragment-pooled `cigar_sequence_identity(string_agg(cigar, '') OVER pair)` idiom as the recommended paired-end gate, which is exactly what `align_sharded` uses. (An earlier revision of this file called it "a contract we rely on rather than one we are promised"; it is promised.) It is load-bearing for that gate, which windows with **no `ORDER BY`** — the two mates may concatenate in either order. Pinned by `qiita-compute-orchestrator/tests/jobs/test_align_sharded.py::test_pooled_cigar_scoring_is_permutation_invariant`.
  - **Upstream flags one trap in that idiom we should not rediscover:** `string_agg` **skips NULL CIGARs**, so the pooled form silently degrades to a single-mate identity if one mate is unmapped. Safe under `no_discordant`/`no_mixed` (both mates always mapped); add a guard if those are ever relaxed. Also `string_agg(cigar, '')` — the empty separator is required, since the default comma injects `,` and raises `Invalid CIGAR string`.
  - **Upstream now ships `cigar_pooled_identity` and advises against the concatenation idiom for pooling** ([Pooled sequence identity](https://the-miint.github.io/duckdb-miint/alignment_analysis/#pooled-sequence-identity)): concatenating builds a CIGAR the SAM spec forbids (clipping is only legal at an end), fails outright on a group holding an unmapped record, and is wrong for anything adjacency-sensitive. Identity itself is still additive, so `align_sharded`'s existing pooled gate scores the same number — the aggregate is the form to reach for in new code.
- `cigar_query_intervals(cigar, flags, [type='aligned'])` → `LIST<STRUCT(start BIGINT, stop BIGINT)>` — which positions of the READ an alignment record covers, 0-based half-open, in the read's own orientation (the reverse bit mirrors them, which is what makes records of one read comparable). Field names match `compress_intervals`, so the two compose. [Upstream](https://the-miint.github.io/duckdb-miint/alignment_analysis/#cigar-query-intervals). Pinned in `qiita-common/tests/analytic/test_circular_gate_contract.py`.
- `cigar_pooled_identity(cigar)` — **an AGGREGATE**: identity for a read the aligner reported as several records, `sum(match_ops) / sum(alignment_columns)` over the group. NULL under the same conditions `cigar_sequence_identity` is, plus when the group mixes legacy `M` with `=`/`X` across records. [Upstream](https://the-miint.github.io/duckdb-miint/alignment_analysis/#pooled-sequence-identity). Reached through `circular_query_coverage`'s `identity` column rather than called directly.
- `mask_dust(sequence, [hardmask=false])` — low-complexity masking
- `merge_pairs_vsearch(fwd_seq, fwd_qual, rev_seq, rev_qual, [options])`

Takes **native-integer** `reference`/`sample_id` (BIGINT/UUID/VARCHAR; `feature_id` inherits `reference`'s type) with **no `::VARCHAR` casts** — requires the id-type-preservation fix (`9f31276`; earlier builds forced a VARCHAR `feature_id` and aborted on a BIGINT `reference`). Rejects a non-id `reference` type with a clean BinderException; rejects an all-NULL `sample_id` source (empty input). Consumed by `estimate_feature_table`.

So woltka counts per SEGMENT, distinguishing mates only when `0x40`/`0x80` tell them apart; a lone mate is 1.0 either way. **A fixture carrying `flags = 0` for paired data therefore under-counts every pair by half**, silently — which is what makes realistic flags load-bearing in any test that asserts count values.

AS c`, which is exactly what `genome_coverage` does internally — so grouping by one more key is re-using that macro's own method, not inventing an analytic.
  - **Three silent behaviours, each of which yields a plausible wrong number rather than an error.** (1) **An inverted interval is swapped, not rejected** — `(10, 4)` returns `[4, 10)`, so transposed arguments produce a confident wrong answer. (2) **A NULL in *either* argument drops that row from the group** silently (an all-NULL group is indistinguishable from an empty one). (3) **An empty group returns NULL**, and `UNNEST(NULL)` yields **zero rows** — so a downstream `SUM` is NULL, not `0`. For a coverage denominator that is usually right (no alignments must not survive a threshold), but it is a NULL, so `COALESCE` if you need a literal zero. A zero-length interval `[3, 3)` is retained as a list element and contributes 0.

- `shear_tree(tree_table, tips_table, [collapse=true], [ignore_missing=false])` — prunes a tree to a keep-set of tips. **qiita-verified 2026-08-13, mirror build `2b2841e`** (catalog probe + behaviour probe; the mirror build matters — see below). Both positional args are relation NAMEs, resolved on a SEPARATE connection like the sharded aligners'; a TABLE and a VIEW both resolve. `tips_table` needs a `name` VARCHAR column (duplicate and NULL names ignored); `tree_table` needs `read_newick` shape (`node_index`, `parent_index`, `name`, `branch_length`, `edge_id`). Output is `(node_index, name, branch_length, edge_id, parent_index, is_tip)`, reindexed 0-based, `UNION ALL`-compatible with `read_newick`.
  - `collapse := true` (the default) removes single-child ancestors and **sums their branch lengths onto the surviving edge**, so tip-to-tip distances are preserved, and the LCA of the kept tips becomes the new root. Measured: an ancestor at 0.1 above a tip at 0.2 yields `0.30000000000000004` — a float sum, so compare approximately. The collapsed edge keeps the surviving lower node's `edge_id`; the new root's `branch_length` is NULL and its `name` is the **empty string, not NULL**. `collapse := false` keeps every internal node on a retained path, unifurcations and all. A keep-set matching exactly **one** tip does not error — measured, it returns a single-node tree (that tip, `branch_length` NULL, `parent_index` NULL, `is_tip` true), which matters because the adjacent zero-tip case *does* error: a caller must handle "no rows" itself but need not special-case "one row".
  - Two distinct failures, both `InvalidInputException` and both naming what went wrong: a requested tip that is not a tip in the tree → `shear: N requested tip name(s) not found as tips in the tree: 'zz'` (suppress with `ignore_missing := true`), and — **always, regardless of that flag** — `shear: no tips from the requested set matched a tip in the tree`, because a tree cannot be sheared to nothing. A missing `tips_table` is a `BinderException` instead. Only **tip** names are matched; an internal label counts as missing. Note the missing-tip message **lists every name**, so a caller with a six-figure keep-set wants its own count-based check ahead of this one rather than that error.
  - Four more input behaviours, **qiita-verified 2026-08-13** on the same build, each one a thing a caller renaming tips has to know. `tree_table` may carry **extra columns** (`is_tip`, `feature_idx`, anything) — they are ignored, so a projection is a memory choice and not a binder requirement. A **NULL-named tip** is simply unmatched and pruned, which makes NULL the safe way to say "not in the keep-set" while rewriting names. **Duplicate tip names are KEPT, both of them** — the shear does not notice, so two tips renamed to one handle publish a tree with a repeated tip label and no error. A **duplicate `node_index`** is caught, `Failed to build tree from 'x': Duplicate node_id: 0` — which names a node id rather than the cause, so a rename that fans out (a feature under two genomes, `feature_genome` being many-to-many) is worth catching before the call. An **empty `tree_table`** is `Tree table 'x' is empty`, naming the relation, so a reference with no phylogeny reads as an internal error unless the caller detects it first.
  - **Absent from older builds.** It is in the mirror `2b2841e` and NOT in `d0336e9`, which is what a stale `~/.duckdb/extensions` may still hold — and the client `connect_with_miint()` path `INSTALL`s without ever force-refreshing, so the symptom is a bare `Catalog Error`. Probe the build, and clear `"$TMPDIR"/qiita-*-duckdb-ext` before believing an absence — `qiita_common/duckdb_miint.py`'s `setup_miint_test_env` documents why that cache never refreshes itself.
  - Upstream notes the build is single-threaded and allocation-bound on large trees, and suggests preloading jemalloc process-wide for a ~30% win; it is a speed knob only, not a memory one.

Named opts include `preset` (e.g. `'sr'`) and `max_secondary` (`:= 0` to drop secondary alignments). **`max_secondary := 0` is NOT "primary alignments only", whatever the upstream reference says** ([duckdb-miint#255](https://github.com/the-miint/duckdb-miint/issues/255), docs-only): it bounds minimap2's `-N`, i.e. SECONDARY (`0x100`) records, and a SUPPLEMENTARY (`0x800`) record from a split alignment survives it. **qiita-verified 2026-08-24** (mirror `9fc4d12`): a 6 kb read across a 20 kb subject's start/end junction returns the same two rows at `max_secondary := 0` and at `100`, the second `flags = 2048`; an interior control is one row in both. A control read on an unrelated subject is 1 row at every setting. A subject scoring materially below the best is not reported at ANY cap: at `max_secondary := 100`, 95%-identical subjects give 0 rows beside an exact match while giving rows when the exact match is absent. The knob that decides that (`-p`) is not exposed — [duckdb-miint#189](https://github.com/the-miint/duckdb-miint/issues/189), open; we have no workaround and do not need one, since `align_denovo` wants near-tie placements rather than competitive placement. Writes SIX files under the prefix (`index.{1..4}.bt2`, `index.rev.{1,2}.bt2`), so `output_path` is a prefix and `reference_index.fs_path` is that prefix. **It DOES require the gpl-boundary binary** — an earlier revision of this file said "needs no `install_gpl_boundary()`", which is wrong and was probably an artifact of probing a host that already had the binary on `PATH`. `src/save_bowtie2_index.cpp:28` throws `gpl-boundary binary not found` if it is absent, and errors again if the daemon does not advertise `bowtie2-build` (needs **≥ v0.2.0**). - `align_bowtie2_sharded(query_table, shard_directory:=, read_to_shard:=, [max_secondary, include_shard_name, preset, …])` — the bowtie2 twin of `align_minimap2_sharded`. **qiita-verified 2026-07-09** (smoke + probe): same table-NAME resolution, `read_to_shard` shape, and 21-column output, EXCEPT `shard_directory` holds one SUBDIR per shard (`{shard_name}/index.*.bt2`), and — unlike minimap2 — a query batch must be UNIFORMLY single- OR paired-end: a MIX of null and non-null `sequence2` raises `gpl_boundary: … all must be non-null for paired-end`. A read set is uniformly SE or PE by construction (a prep/run is one or the other), so this rejection is the aligner enforcing that invariant, NOT a signal to split: `align_sharded` feeds a single uniform query and lets both aligners handle the mode natively (a mix is invalid input). No `preset` needed (a bowtie2 index is preset-independent). Consumed by `align_sharded`.
- **Both sharded aligners read `query_table` ONCE PER SHARD** — the cost model the align block size is chosen against. **qiita-verified 2026-07-29** (build `d0336e9`, DuckDB 1.5.4): with the read set held fixed at 40 reads and every read routed to every shard, miint's own `debug := true` per-shard phase log shows **exactly `n_shards` query reads** — 1 shard → 1, 2 → 2, 4 → 4, 8 → 8 (`SET threads=1` to serialise; the log emits a start *and* a completion line per phase, so count one marker). Matches the source on both paths: minimap2 does `ReadShardIds` then a bulk `ReadBatchByIds(query_table, …)` per shard (`src/align_minimap2_sharded.cpp:299`/`:313`, `src/sequence_table_reader.cpp:391`/`:431`); bowtie2 opens a per-shard cursor `SELECT q.read_id, q.sequence1[, q.sequence2][, q.qual1][, q.qual2] FROM <query> q JOIN <read_to_shard> rts ON q.read_id = rts.read_id WHERE rts.shard_name = '<shard>'` (`OpenCurrentShardStream`, `src/align_bowtie2_sharded.cpp:750-771`, called per shard at `:1125`). **So a block's total re-read is `n_shards × block_bytes`, and it is driven by BYTES, not read count.** The per-shard predicate means DuckDB *could* prune row groups, but does not usefully at qiita's 1000-shard configuration: a row group survives if it holds ≥1 of the shard's reads, so touched ≈ `G·(1 − e^(−S/G))`, and with `PARQUET_OPTS` short reads hitting DuckDB's 122880-row cap, `G ≈ N/122880` and `S ≈ N/1000` give `S/G ≈ 123` **independent of N** — every row group holds some of every shard's reads. This is why `align_planner` sizes long-read blocks on bytes (1M reads) rather than inheriting the short-read 10M; see `_LONG_READ_BLOCK_TARGET_READS`. Filed upstream as **[duckdb-miint#184](https://github.com/the-miint/duckdb-miint/issues/184)** (read the query once, or cache the per-shard fetch, or expose a materialize hint), with our workaround's removal tracked at [the-miint/Qiita#392](https://github.com/the-miint/Qiita/issues/392) — see [Open upstream gaps](#open-upstream-gaps).
- **What you pass as `query_table` therefore matters: a Parquet-backed VIEW makes every per-shard read pay for the block's whole sequence bytes; an in-memory TABLE does not.** **qiita-verified 2026-07-30** (DuckDB 1.5.4, no miint — this is a DuckDB scan-cost property, measured against the real bowtie2 per-shard cursor shape above). Conditions: 1000 shards, membership **scattered** (`hash(read_id × prime) % 1000` — a contiguous id range prunes row groups and measures nothing), `threads=8`, warm page cache, zstd Parquet at the repo's 64 MB `ROW_GROUP_SIZE_BYTES`, median of 5 shards. Per shard:

  | query relation | 1M × 160 bp (49 MB) | 1M × 320 bp (99 MB) | 10M × 160 bp (493 MB) | 10M × 2×160 bp PE (986 MB) |
  |---|---|---|---|---|
  | Parquet view | 20.0 ms | 34.9 ms | 169.0 ms | 330.5 ms |
  | in-memory TABLE | 3.4 ms | 3.5 ms | 27.2 ms | 40.0 ms |

  **The two scale on different axes, which is the part that is easy to get wrong.** The view tracks total BYTES — it grows with read count *and* read length (+75% from 160 → 320 bp at fixed count). The table tracks reads-per-shard only and is **flat in read length** (3.4 → 3.5 ms), because DuckDB scans a narrow id column and fetches sequences only for the rows the shard asked for. Over 1000 shards: **169 s → 27 s** for a 10M-read SE short block, **331 s → 40 s** for the PE one, and — extrapolating the view along the byte axis — near **26 min → seconds** for a 1M-read HiFi block at ~15 kb (~15 GB, too large to measure on a dev box, so that one is an extrapolation from 9.4× below it). Building the copy costs one full Parquet scan: **22 ms** at 1M reads, **241 ms** at 10M. Do not derive a per-1000-bp/read slope from one read count and apply it to another — doing exactly that understated the short-read case by 10× while this was being written.

### QC — fastp algorithm port (`docs/qc.md` upstream)
The fastp-equivalent read-QC functions, consumed by the `qc` native job (the bcl-convert → `fastq` → **`qc`** → `host_filter` pipeline). Pinned by `qiita-compute-orchestrator/tests/jobs/test_qc_miint_contract.py`. `qual` is `UTINYINT[]` (phred-decoded, exactly what `read_fastx` / `fastq_to_parquet` emit). Each returns a `STRUCT`.

**All take POSITIONAL args only — named params (`min_length := 100`) raise a `BinderException`, and there are no partial arg lists**: each function has exactly two arities, a short one and a full one. To change one threshold you must restate them all. Upstream writes these as `filter_read(seq, qual [, min_length, max_length, …])`, which *reads* as independently-optional args — it is not. (An earlier revision of this file blamed "named optionals in the upstream docs"; `docs/qc.md` contains no named-parameter syntax at all — the bracket notation is the actual source of the confusion.) Filed as **[duckdb-miint#188](https://github.com/the-miint/duckdb-miint/issues/188)**. **qiita-re-verified 2026-07-30** on build `97a3fff`: a 3-arg `filter_read` raises `No function matches … Candidate functions: filter_read(VARCHAR, UTINYINT[]) / filter_read(VARCHAR, UTINYINT[], INTEGER × 6)`.
- `filter_read(seq, qual [, min_length, max_length, qualified_q, max_unqualified_pct, max_n, min_avg_q])` → `STRUCT(passed BOOLEAN, fail_reason VARCHAR, length UINTEGER, n_bases UINTEGER, low_qual_bases UINTEGER, mean_quality FLOAT)`. Only a **2-arg** and an **8-arg** overload exist (no partial). The 2-arg defaults equal `(15, 0, 15, 40, 5, 0)` — these ARE fastp's defaults — so a faithful `fastp -l 100` is the 8-arg call `filter_read(seq, qual, 100, 0, 15, 40, 5, 0)`. `fail_reason` is `NULL` when passed, else `'length'` / `'n_base'` / `'quality'` / `'too_long'`.
- `trim_adapters(seq, qual, adapter [, match_revcomp, min_match, allow_pre_start])` → `STRUCT(sequence VARCHAR, quality UTINYINT[], trimmed_5p UINTEGER, trimmed_3p UINTEGER)`. `adapter` is `VARCHAR` **or** `VARCHAR[]` (a known-adapter set). The single-end path.
- `trim_adapters_pe(seq1, qual1, seq2, qual2 [, adapters VARCHAR[], overlap_require, overlap_diff_limit, overlap_diff_percent_limit, match_revcomp, min_match, allow_pre_start])` → `STRUCT(sequence1, quality1, sequence2, quality2, overlap_len INTEGER, adapter_trimmed BOOLEAN, trimmed1_3p UINTEGER, trimmed2_3p UINTEGER)`. Only a **4-arg** (overlap-only) and an **11-arg** overload. The 11-arg form with an **empty** adapter list + `(30, 5, 20, false, 0, false)` reproduces the 4-arg result exactly — those are fastp's overlap defaults — so pass a non-empty `adapters` to add the by-sequence adapter fallback fastp applies *after* overlap analysis, without changing overlap behavior.
- `trim_polyg(seq, qual [, min_len, max_mm, max_window_mean_q])` → `STRUCT(sequence, quality, trimmed_5p, trimmed_3p)`. Trims a 3' G-run **only when its quality is low** (2-color no-signal); a high-quality G-run is left intact. Defaults `(10, 5, 5)`. fastp enables polyG only for 2-color instruments (NextSeq/NovaSeq), so the `qc` job calls it gated on `instrument_model`.
- `trim_polyx(seq, qual [, min_len, max_mm])` → same `STRUCT` as `trim_polyg`. Trims **any** 3' homopolymer run (A/C/G/T), with no quality gate — unlike `trim_polyg`. 2-arg or 4-arg. Not used by the `qc` job today; listed so nobody concludes miint lacks it. Upstream notes miint's tie-break between equal-length runs is a deterministic ACGT order, where fastp's is not — so this diverges from fastp by design.
- `qc_version()` → `VARCHAR` — QC-port version sanity probe (`qc 0.1.0 (port of fastp algorithms)` on `97a3fff`).

**2. The source, when you need certainty** (checking whether docs lag a build, or chasing an `Unknown option` error). Every writer validates options in one `if`/`else if` chain, so the valid set is one grep against a miint checkout — authoritative by construction, because that chain *is* the validator:

```bash
  | grep -oE '"[a-z_0-9]+"' | tr -d '"' | sort -u
```

`src/copy_sam.cpp` backs **both** `FORMAT SAM` and `FORMAT BAM`; the others are `copy_ubam.cpp`, `copy_fastq.cpp`, `copy_fasta.cpp`, `copy_biom.cpp`, `copy_newick.cpp`. Run against `97a3fff` (2026-07-30):

**This table is a worked example of the recipe, not a reference to trust** — it is exactly the kind of mirror that rotted this file before. Re-run the grep rather than reading the row. It is included because it already earned its keep: it shows `FORMAT FASTQ` accepts `id_as_sequence_index`, `include_comment` and `qual_offset`, none of which the `FORMAT FASTQ` writer notes below mention — so if those notes look like the complete surface, they aren't.

**Two things that are already safe:** unknown options are **rejected**, not ignored (`COPY … (FORMAT BAM, SEQUENCEDATA 'x')` → `Binder Error: Unknown option for COPY FORMAT SAM: SEQUENCEDATA`), so a typo cannot silently no-op. And a `BinderException` naming one required option is proof a full option list exists — go read it, don't just add the one it named.

**Reads BAM vs alignment BAM — use the right one.** `FORMAT SAM` / `FORMAT BAM` is an ALIGNMENT writer: it takes HTSlib-style alignment columns, and by default writes SEQ/QUAL as `*` (pass `SEQUENCE_DATA` to fill them — see the writer notes below). It still can't write a *reads/uBAM*: even with `SEQUENCE_DATA` it emits alignment records under an `@SQ` header, not headerless unaligned reads. For an **unaligned reads BAM** use **`FORMAT UBAM`** (duckdb-miint#156, shipped in #157): it writes `read_id`/`sequence1`/`qual1` as name/SEQ/QUAL with no `@SQ` header, takes a `READ_GROUP {…}` struct and a `TAGS {tag: column}` map for per-read integer tags. `lima_export` uses it to build the CCS BAM lima needs (`@RG … DS:READTYPE=CCS`, a per-read `zm` tag); its call is `_UBAM_COPY_SQL`, the single place that shape lives.

**`FORMAT BAM` writer — qiita-verified 2026-07-24** (supersedes a 2026-07-22 pass whose `@SQ`-order claim was wrong; probes + `qiita-compute-orchestrator/tests/jobs/test_assembly_coverage.py`; consumed by the `assembly_coverage` native step, whose BAM feeds metaWRAP's `jgi_summarize_bam_contig_depths`). Full parameter list upstream at <https://the-miint.github.io/duckdb-miint/writing/#sequence-data> — the notes below are the qiita-relevant subset, not the whole surface:
- **`REFERENCE_LENGTHS` is required whenever the header is written** (`INCLUDE_HEADER=true`, the default): the plain `(FORMAT BAM)` form raises `Binder Error: COPY FORMAT BAM requires REFERENCE_LENGTHS parameter`. It names a **persistent table** with columns `(reference, length)`.
- The `@SQ` header carries **every** contig in that table, including ones with zero alignments — which is what makes a downstream depth tool report them at 0 rather than dropping them.
- **`@SQ` is sorted by reference NAME, and is not steerable from the reference-lengths table.** [duckdb-miint#173](https://github.com/the-miint/duckdb-miint/issues/173) gave it a defined order; before that it was `unordered_map` hash-bucket order, equal to neither the reflen table's physical order nor its reverse nor `ORDER BY reference` (qiita-probed 2026-07-24 at n = 5, 10, 64, 300, 2000, built ASC/DESC/shuffled — deterministic, but the rule was unknown). That earlier entry had claimed `@SQ` came out REVERSED, which held only at tiny n, and the false claim cost a production ticket (`binning` died in `jgi_summarize_bam_contig_depths` 2.15 with `the bam file 'reads.bam' is not sorted!`). Read `@SQ` back with [`read_alignment_header(path)`](https://github.com/the-miint/duckdb-miint/issues/174) → `(tid, reference, length)`, the only way to see tid from SQL.
  - **There is no sort parameter, and none is needed for a coordinate sort.** The documented `FORMAT SAM`/`FORMAT BAM` parameter list is exactly `INCLUDE_HEADER`, `REFERENCE_LENGTHS`, `SEQUENCE_DATA`, `COMPRESSION` (SAM only) and `COMPRESSION_LEVEL` (BAM only). A BAM is coordinate-sorted by *tid*, and tid order is name order, so `ORDER BY reference, position` on the copied relation IS the coordinate sort — which is what `assembly_coverage` now writes, letting `binning.sh` stage its BAM for metaWRAP with no `samtools sort`. **qiita-verified 2026-08-03** (miint `2b2841e`, DuckDB 1.5.4; consumers on the `long-read-assembly-binning-1.0.0` image's pins — metabat2 2.15, samtools 1.10), with the same BAM written without the `ORDER BY` as the control: `jgi_summarize_bam_contig_depths` 2.15 rejects the control and accepts the ordered file, reporting a depth/variance matrix identical to the one it gets from a `samtools sort` of that same file; `samtools index` 1.10 likewise fails on the control and succeeds on the ordered file. **The `ORDER BY` survives `preserve_insertion_order=false`** (which every job of this shape sets) **at scale**: 2M records over 20,000 references, `threads=8`, `memory_limit` low enough that the sort spilled — fully tid-monotonic, 0 backsteps, identical to the `preserve_insertion_order=true` control, against 999,778 backsteps for the same relation copied without the `ORDER BY`. Re-measure at scale, not on a small fixture: a write that fits one batch cannot expose a sink that reorders batches.
  - **Second consumer, and it does NOT go away with the sort:** the depth matrix `jgi_summarize_bam_contig_depths` writes follows `@SQ` order, and **metabat2 aborts** unless the assembly FASTA is in that same order (`the order of contigs in abundance file is not the same as the assembly file: <contig>`). Record ordering is irrelevant to this — it never moves an `@SQ` line — so `binning.sh` reorders the assembly FASTA into `@SQ` order via `samtools faidx`. qiita-verified on the shipped samtools 1.10 / metabat2 2.15. Removing it needs either a steerable `@SQ` upstream or a name-ordered assembly — see [Open upstream gaps](#open-upstream-gaps).
- No `@HD` line is written by miint's `FORMAT BAM` writer, so its output carries no `SO:coordinate` tag. Neither of our consumers wants one — both inspect the actual record order, and jgi and `samtools index` accept a tagless coordinate-sorted file (verified above). [duckdb-miint#202](https://github.com/the-miint/duckdb-miint/issues/202) proposes a `SORT_ORDER 'coordinate'` that would validate record order and stamp `@HD VN:1.6 SO:coordinate`; a `samtools sort`ed BAM carries that tag today, verified.
- **`SEQUENCE_DATA 'table'` writes real SEQ/QUAL** — use it whenever anything downstream measures coverage. The table needs `read_id` / `sequence1` / `qual1` (`UTINYINT[]`, exactly what `read_fastx` emits); `sequence2`/`qual2` for paired. Without it SEQ is `*`. Adding a sequence *column* to the copied relation does **not** work and does not error — extra columns are silently ignored. A `read_id` in the alignment that is absent from the table is a hard error (`Invalid Input Error: Read '<id>' not found in SEQUENCE_DATA table`), not a silent `*`, so a partial lookup fails loud. Hard-clipped and reverse-strand records are handled correctly (SEQ trimmed to the CIGAR, reverse-complemented) — `samtools quickcheck` clean.
- **Why that matters concretely** (measured against `jgi_summarize_bam_contig_depths` 2.15): jgi excludes up to `--maxEdgeBases` (default 75) at each contig end from the depth mean, and sizes that window from the read length, which it reads out of SEQ. With SEQ absent (`seqlen=0`) the window collapses, the under-covered contig ends are averaged in, and depth drops by about `2*75/contig_length` — 0.750% on a 20 kb contig vs 0.750% predicted. The bias is **inversely proportional to contig length, not a constant offset**, and it inflates the reported variance too, so a consumer clustering on differential coverage (metabat2) sees a length-correlated distortion. With `SEQUENCE_DATA` the depth *and* variance match a real `minimap2 | samtools sort` BAM to every printed digit, and jgi's per-record warnings stop.

**`FORMAT FASTQ` writer — qiita-verified 2026-06-25** (probes + `qiita-compute-orchestrator/tests/jobs/test_masked_export_fastq_contract.py`, build `eca0e79`; consumed by the `qiita-admin masked-read-export` CLI writing the data plane's `read_masked` macro to per-sample FASTQ):
- Requires the **verbatim** columns `read_id`, `sequence1`, `qual1` (and `sequence2`, `qual2` for paired) — the exact names `read_masked` emits. Aliasing `read_id` away raises a `BinderException`; select the macro's columns by name.
- `qual1`/`qual2` are `UTINYINT[]` (phred-decoded, as `read_fastx` emits) and are written back ASCII **phred+33** (Q40 → `I`, Q30 → `?`).
- A row with `sequence2` set into a **single** output path errors; paired output needs either the **`{ORIENTATION}`** placeholder in the path (split files) or **`INTERLEAVE true`** (one interleaved file).
- `{ORIENTATION}` expands to exactly **`R1`** / **`R2`**, so `TO '<stem>.{ORIENTATION}.fastq'` yields `<stem>.R1.fastq` + `<stem>.R2.fastq`.

**`FORMAT BIOM` writer — qiita-verified 2026-08-12** (probes + `qiita-control-plane/tests/test_biom_writer_contract.py`, build `2b2841e`; consumed by the client-side feature-table recipe, which writes the relabelled table a user publishes). Writes a **BIOM 2.1 HDF5** file. Every row below has a test, because three of these are decisions the writer makes silently on the caller's behalf:
- **Required columns, BY NAME:** `feature_id` VARCHAR, `sample_id` VARCHAR, `value` **DOUBLE**. A missing one is a `BinderException` naming it; column *order* is irrelevant. `value` must be DOUBLE **exactly** — `FLOAT`, `DECIMAL` and `BIGINT` are all refused, so an unquoted decimal literal (which types as DECIMAL) fails to bind.
- **Any OTHER column is silently ignored.** A relation still carrying an internal identifier writes a perfectly valid BIOM with that column dropped on the floor — so the writer is *not* a guard against leaking one, and the caller's projection is.
- **Duplicate `(feature_id, sample_id)` pairs are SUMMED**, with nothing in the file recording it (`src/BIOMTable.cpp`'s `compress_coo`). Two features relabelled to one public id therefore merge into one row of the published table, invisibly — which is why the recipe refuses that collision before writing.
- **Zero values are dropped** (BIOM is sparse), so a BIOM and a Parquet of the same relation can legitimately differ in row count.
- **NULL or empty-string ids are refused** (`InvalidInputException`), and the failed write leaves **no file behind**.
- **It refuses to overwrite an existing file** — `IOException: Cannot overwrite existing file '…'. Delete it first…` — unlike the Parquet COPY, which replaces silently. This applies to any target, including a `.partial` sibling left by a killed process, so an atomic-write caller must clear its own partials or every retry fails on one.
- **An empty relation writes a valid, readable file** (0 rows back through `read_biom`), so a legitimately empty result needs no special case.
- Options are `COMPRESSION` (`'gzip'`/`'gz'`/`'none'`, default gzip), `GENERATED_BY` (default `miint` — the library, not the caller), and `ID` (default the literal `No Table ID`). Unknown options are rejected, not ignored.
- **gzip can make a small table BIGGER**: 200 non-zero entries measured 37 808 bytes gzipped against 30 336 uncompressed (per-dataset HDF5 deflate overhead). It is still the right default at real table sizes.
- `read_biom(path)` reads it back as `(sample_id, feature_id, value)` — the same triple, one row per non-zero entry — which is the only round trip available from SQL.

**`FORMAT NEWICK` writer — qiita-verified 2026-08-13** (probes against mirror build `2b2841e`, plus the option chain read out of `src/copy_newick.cpp`). **Nothing in qiita emits Newick**: the client-side feature-table recipe considered it for its sheared tree and writes Parquet instead, so the consumer chooses whether to convert and the edge-id default below is theirs to make rather than ours. Recorded because that decision was made against these probes:
- **Required columns, BY NAME: `node_index` and `parent_index` only** — each missing one raises `BinderException: COPY FORMAT NEWICK requires '<col>' column`. `name`, `branch_length` and `edge_id` are optional, and any other column (`is_tip`, `filepath`) is silently ignored, so `shear_tree`'s output can be passed through as-is.
- **`EDGE_IDS` defaults to ON whenever an `edge_id` column is present** (`copy_newick.cpp`: the flag is set from the column's presence when the option is not given), writing jplace-style `{N}` annotations after each branch length: `(t1:0.3{11},t3:0.4{13});`. Documented upstream, and worth knowing anyway because **`shear_tree`'s output carries `edge_id`, so passing it straight through — the shape `docs/phylogeny.md` reaches for — writes annotated rather than plain Newick.** Suppress with `EDGE_IDS false` or by not selecting the column: measured byte-identical (`((t1:0.2,t2:0.3)innerA:0.1,t3:0.4);`), as is passing an all-NULL `edge_id`. Prefer omitting the column — an option can be forgotten, a missing column cannot.
- Surviving internal-node names are written; a root whose `name` is the empty string writes as an unnamed root.
- Options are `COMPRESSION` (auto-detected from a `.gz` path, so `TO 'x.nwk.gz'` needs no option), `EDGE_IDS` (BOOLEAN), and `PLACEMENTS` (a table/view name, whose schema is validated at bind time). Unknown options are rejected, not ignored.
- `read_newick(path)` reads it back, which is the only round trip available from SQL.

## Internals worth knowing before extending qiita usage

These are not just curiosities — they constrain how qiita's data-plane and orchestrator code may call miint.

- **GPL boundary (`install_gpl_boundary`) — it covers bowtie2 and FastTree, and nothing else we use.** The extension is BSD; FastTree and bowtie2 are GPL, so they are statically linked into a separately-distributed [`gpl-boundary`](https://github.com/the-miint/GPL-boundary) binary that miint launches as a child process (JSON-line control channel + POSIX shared memory). **Exactly five source files touch it** — `align_bowtie2.cpp`, `align_bowtie2_sharded.cpp`, `save_bowtie2_index.cpp`, `phylogeny_fasttree.cpp`, `install_gpl_boundary.cpp`. So the functions that need the binary installed are `align_bowtie2`, `align_bowtie2_sharded`, `save_bowtie2_index` and `phylogeny_fasttree`.
  - **An earlier revision of this file said the boundary hosts "notably `vsearch`, MAFFT, SortMeRNA". It does not, and that error costs work in the expensive direction** — it implies a deploy-time dependency for functions that have none. vsearch and MAFFT are linked **statically, in-process** (`libvsearch.a`, `libmafft_parttree.a`), and `align_sortmerna.cpp` links the static SortMeRNA bundle with no boundary involvement. **`merge_pairs_vsearch`, `detect_chimera_uchime*`, `cluster_sequences_vsearch`, `search_sequences_vsearch`, `align_mafft` and `align_sortmerna*` need NO `install_gpl_boundary()`.** (The daemon separately advertises `sortmerna` and `prodigal`, but miint does not route to them.)
  - Availability probes are per-tool, not global: `phylogeny_fasttree_available()` covers FastTree only. The bowtie2 functions fail loud at session boot with an install hint; `align_bowtie2*` additionally gate on daemon **≥ 0.4.2**, while `save_bowtie2_index` accepts **≥ 0.2.0** (see its inventory entry).
- **Per-sample `sample_id='col'` knob** (see `internals/per-sample-pattern.md`). When the user passes `sample_id='some_column'`, the function partitions by that column and runs the tool per group. Reserved output column names are listed in that doc — avoid colliding with them in qiita's table schemas.
- **Reading tables/views inside table functions** (`internals/reading-tables-views.md`). miint table functions use a **separate** DuckDB connection during bind/execute, so a call that names another table (`read_alignments(..., reference_lengths='ref_lens')`, `align_minimap2(query_table, subject_table=...)`) resolves that name over there, not on yours. Since [duckdb-miint#193](https://github.com/the-miint/duckdb-miint/issues/193) that helper connection shares the caller's temporary objects, so `TEMP TABLE`s, `TEMP VIEW`s and **registered Arrow relations** (a DuckDB `register()` produces a temporary view) resolve there. **Measured on staged build `9fc4d12`, 2026-08-23, for `align_minimap2`, `save_minimap2_index`, and `woltka_ogu` without `sample_id`** — the general rule is #193, and confirming any other single function is a three-arm probe (base TABLE as control, TEMP TABLE, registered Arrow). qiita comments asserting invisibility for a function NOT in that measured list have not been re-checked; `build_rype_index` and `host_filter` (rype paths) are the ones still carrying it. Two things do not resolve, and they are different in kind:
  - **CTEs**, on any path — a CTE is not a catalog object. Stage it.
  - **miint's fixed-temp-name paths**, which use a connection that does NOT inherit: `massql`, and the per-sample (`sample_id := …`) branches of `uchime_ref` / `sylph_profile` / `woltka_ogu` — [duckdb-miint#207](https://github.com/the-miint/duckdb-miint/issues/207), open. These need a regular non-temp TABLE. **qiita-verified 2026-08-23, staged build `9fc4d12`:** `woltka_ogu('t','sequence_idx', sample_id := 'prep_sample_idx')` returned rows over a base TABLE and `Catalog Error: Table with name … does not exist!` over both a `TEMP TABLE` and a registered Arrow relation, while the same call **without** `sample_id` resolved all three. `qiita_common.feature_table`'s staging uses the per-sample form, which is why every relation it stages is a regular TABLE.
  - Separately from visibility: a registered Arrow **stream** (`RecordBatchReader`) is consumed exactly once — a second scan returns zero rows silently — so a multi-pass consumer needs a materialized relation regardless of whether the name resolves. Per [duckdb-miint#229](https://github.com/the-miint/duckdb-miint/issues/229)'s resolution (upstream's account, not measured here): `align_minimap2_sharded` now buffers the relation once into a per-shard TEMP table, while `align_bowtie2_sharded` keeps streaming per shard — buffering would break larger-than-memory input — and fails loud instead, naming `CREATE TEMP TABLE q AS SELECT * FROM <rel>` as the fix.
- **Arrow zero-copy** (`internals/arrow-zero-copy.md`). RYpe and a few others move Arrow batches across the FFI without copying — lifetime is tied to the source batch. If we ever embed miint outside DuckDB, mind the lifetime rules.
- **Identifier-column codec** (`id_column_codec` / `id_column_utils` in `internals/architecture.md`). miint preserves arbitrary user identifier columns (e.g. `read_id`) through alignment/classification pipelines. We rely on this to carry our `prep_sample_idx` and friends through alignment.
- **Dual-path table functions (standard + lateral) and filter pushdown.** Most readers support both `SELECT * FROM read_fastx('x.fq')` and `… JOIN LATERAL read_fastx(t.path)`. Predicate pushdown into `read_alignments` is real — `WHERE flag & 4 = 0` will prune at the HTSlib layer. Don't write helper macros that materialize before filtering.

## Embedded tool versions — ask the binary, never a table

Bioinformatics tools change results between versions (minimap2 secondary-alignment counts, vsearch chimera scoring, SortMeRNA e-values). Those tools are compiled **into** the miint extension, so the versions you get are fixed by **which `.duckdb_extension` file was loaded** — not by the conda env, not by anything on `PATH`. Two qiita components on different miint builds can legitimately produce different numbers from identical input.

**`miint_versions()` reports every one of them at runtime.** Use it; there is no version table in this file on purpose, because the one that used to be here drifted (it claimed WFA2-lib 2.3.5 when the build had 2.3.6) and mislabelled three tools' link type.

```sql
SELECT * FROM miint_versions();
```
```
miint 97a3fff │ htslib 1.22.1 │ minimap2 v2.30-1-g0477498 │ kseq++ 1.1.2 │ WFA2-lib v2.3.6
rype 1.0.0-rc.2-35-gd7889ed │ vsearch v2.30.5-miint-133-gbb445596 │ mafft v7.471-miint-5-g956a103
abpoa 950d55b │ sylph 203760b │ unifrac v1.6.1-5-g91c2600 │ scikit-bio-binaries v1.0.3-16-g372eb9b
HDF5 1.14.6 │ zlib 1.3.1.zlib-ng │ libdeflate 1.24 │ libcurl 8.16.0-DEV
```

Two things it does **not** cover, because they are not compiled in — they are ordinary executables found on `PATH` at runtime, so they can differ per host even on one miint build:
- **`gpl-boundary`** — the bowtie2 + FastTree host (see the [GPL boundary bullet](#internals-worth-knowing-before-extending-qiita-usage)). Version-gated: `align_bowtie2*` need ≥ 0.4.2, `save_bowtie2_index` ≥ 0.2.0.
- **IBM Aspera `ascp`** — ENA transfers.

**When a result looks tool-version-dependent, run `miint_versions()` on each host first.** That is usually faster than debugging qiita, and it is the one question this file cannot answer for you.

## Keeping this doc fresh

To keep this file honest:

miint is a first-party dependency built by the same org, and it behaves like one: in the 2026-07-30 audit of this file, **every function it named still existed** and nothing had been removed — miint had only added and fixed things. Assume that. The failure mode here has never been miint breaking us; it is this file mirroring upstream and the mirror going stale.

1. **Check the `Last checked:` date in the header** before relying on a specific signature.
2. **Read upstream's own index**, [`docs/table_of_contents.md`](https://github.com/the-miint/duckdb-miint/blob/main/docs/table_of_contents.md). It lists every doc file and what is in it. That is the authoritative map; the [table above](#upstream-docs-map) is a convenience shortlist of what qiita consumes.
3. **Ask the binary for anything you need to be sure about.** Upstream docs can lag the build in either direction, and qiita runs the build:
   ```sql
   LOAD miint;
   SELECT * FROM miint_versions();                      -- what is actually compiled in
   SELECT function_name, parameters, parameter_types    -- real signatures + overload arities
   FROM duckdb_functions() WHERE function_name = 'filter_read';
   ```
   `duckdb_functions()` settled the QC overload arities in this file — it shows exactly which argument counts exist, which prose notation does not.
4. **What NOT to copy in:** upstream prose, examples, parameter tables, version numbers. This file is an index plus a record of *qiita-specific* findings — measurements, traps that bit us, workarounds we carry. Depth lives upstream; mirrored depth is what rots.
5. **If this file disagrees with upstream, upstream wins** — but check whether the disagreement is a real miint change or just a stale claim here before "fixing" anything. Fix it in the same commit as the consumer-code change that exposed the drift.
6. **File miint bugs and feature requests upstream**, and put the issue number in [Open upstream gaps](#open-upstream-gaps) in the PR that lands the workaround. Every bug/limitation claim in this file must point at an **open** issue. If the issue closed, the claim is obsolete — delete it and describe the shipped behaviour instead. The 2026-07-30 audit found several stale warnings telling qiita to work around things miint had already fixed.
